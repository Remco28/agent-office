Report on the review-loop skill (read-only; nothing changed). I read SKILL.md in full, the explainer-public and _template profiles, the start of briefs.md, and the first 60 lines of evidence.md. I did not read the code-review or web-app-tasks profiles or the rest of evidence.md.

1. What it is for and how it works

It is a method for checking a piece of work by handing it to readers who have never seen it, then deciding carefully which of their answers to believe. It finds two kinds of problem: coherence (the thing contradicts itself or its source) and comprehension (a stranger does not get what was meant). It cannot judge merit, so the report should say which of the three it is reporting on, and a human always reviews at the end.

The loop: (0) run every mechanical check you can against a source of truth, and keep those as re-runnable scripts. (1) write one success sentence about the reader's task, and get the people who know to confirm any outside rules in plain words. (2) pick a profile, which sets the audience, cast, house rules and sometimes a stop rule. (3) freeze a version, give readers the rendered artifact in parallel and blind to each other, and ask them whether it worked for them rather than what is wrong. (4) sort findings into tiers: tier 1 is verified by two independent readers or checkable against the artifact; tier 2 is one reader plus an outside source, which a second agent tries to kill; tier 3 is taste; tier 0 is a artifact of how it was shown to the reader. (5) fix tier 1 only, prove each fix by counting the old wording across everything and checking the published result, write predictions before the next round, and put any choice that changes what users get to the owner. Each round is recorded in a review-loop/LEDGER.md, and a "believed and wrong" line is required. A disposition auditor checks the ratings every round. Stop after two clean rounds, or when only taste is left, or when the budget runs out.

2. My situation: a finished long API reference for a client's payment service, nobody asked for a review

I do not start the loop. The skill says to run it only when the user asks, and to ask first when the work looks important. A payment API for a client clearly qualifies. So I would tell Frank the reference is ready, say the loop exists, and ask whether he wants it, with a recommended size (a handful of readers and one or two rounds, not twenty readers) and the reason it's worth it (wrong payment docs cost the client money). That is a decision he should confirm, even with my default. While waiting, I would do the step-0 checks myself, since they are ordinary diligence and not the loop: run every example request against the sandbox, check every endpoint, parameter and error code against the real spec or service, and fix any mismatch. Then I'd ask the client's engineers to confirm the business rules (fees, rounding, currencies, idempotency, refund windows) before any reader sees the reference. If he says yes, I'd pick a profile. None fits: explainer-public is for public science pages and its rules (non-detection, association versus cause) are the wrong ones. So I'd copy _template and write rules with tests, for example "every example runs against the sandbox and returns the documented status", "every error code in the reference is returned by some endpoint in the spec", "every term is defined at first use". The success question would be about a task, for example "a developer can issue a partial refund and handle its webhook, looking things up as they go".

3. Unclear, contradictory, or likely to be skipped

- The scope rule is unclear. "Only run when asked" and "ask first if important" are consistent, but the "Never skip these" list says "whatever the size of the job", while the text also says two paragraphs need not get twenty readers. It doesn't say what the minimum is for a small job, or whether the disposition auditor still runs when there are only two readers.
- No profile covers API references. The evidence file says a cold-read test on an API reference found the cast and house rules did not carry over. The skill says to copy _template, but gives no guidance on what to keep from the closest profile.
- Tiering is muddled. Tier 1 includes "checkable against the artifact", which lets a single reader's finding become tier 1 if it contradicts the artifact. Tier 2 is "checkable against an outside source". So "the page contradicts itself" is tier 1 with one reader, but "the page contradicts the spec" is tier 2. Also "fix tier 1 only" sits oddly beside "fix every verified HIGH and MEDIUM" in profiles that have severity.
- Predictions "written before the round" are required, but nothing enforces the timing. An agent could write them after reading results, which the skill itself says is worthless.
- "Stop when a pass finds only details" and "the budget is spent" are vague. There is no budget figure, and "details" is not defined.
- Where the ledger and reader reports go, and whether review-loop/ is committed to git or removed later, is not stated. It says "safe to delete when done", but a client repo may need the record.
- The "Fix auditor" is listed as from round 2, and the "Never retired" disposition auditor is in the table, but the retirement rule (two rounds with no tier-1 or tier-2) is not said to apply to the fix auditor. It is probably meant to be exempt, but it isn't stated.
- Step 3 says to give readers a rendered artifact, but for an API reference the audience meets it as text plus live examples. The skill doesn't say what "rendered" means for that.
- The likeliest skip is step 1, confirming the rules with the person who knows. For a payment API that means the client's engineers, and the skill does not say who they are or what to do if they cannot be reached.
- The likeliest skip overall is the predictions and "believed and wrong" lines, since they are the parts that cost the most discipline and the least effort to leave blank.
